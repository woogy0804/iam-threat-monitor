# iam-threat-monitor

AWS IAM 이벤트를 연결해 의심스러운 행동 흐름을 탐지하고, 판단 이유와 근거 로그를 관제 화면에 표시하는 6인 팀 프로젝트다.

중간발표는 **2026년 10월 8일**이다. 현재 저장소는 기본 구조만 준비한 상태이며, 기능 코드와 AWS 리소스는 아직 구현·배포하지 않았다. 아래 아키텍처는 목표 구성이다.

## 첫 탐지 시나리오

1. 테스트 IAM 사용자에 대해 `CreateAccessKey` 이벤트가 발생한다.
2. 해당 이벤트의 실제 발생 시간으로부터 **10분 이내**에 같은 대상 사용자에 대한 `AttachUserPolicy`가 성공한다.
3. 두 이벤트를 연결해 **검토 필요** 탐지 결과를 생성한다.

작업을 실행한 주체와 작업 대상 IAM 사용자를 구분한다. 연결 기준은 같은 대상 사용자이며, 실행 주체가 같다고 가정하지 않는다. 이 흐름은 정상적인 계정 설정에서도 발생할 수 있으므로 공격이라고 단정하지 않는다.

판단은 수신 시간이 아닌 이벤트의 실제 발생 시간을 기준으로 한다. 같은 이벤트의 중복 전달과 도착 순서 변경을 고려해야 한다. 정확한 시간 경계, 이벤트 성공 판정, 사용자 식별 방식과 상태 보관 정책은 공통 JSON 규격 및 탐지 설계에서 확정한다.

## 목표 아키텍처

```text
테스트 IAM 행동
  → CloudTrail 관리 이벤트
  → EventBridge 규칙
  → Lambda (Python 탐지)
  → DynamoDB
  → 관제 적재 프로그램
  → OpenSearch
  → OpenSearch Dashboards
```

DynamoDB는 이벤트를 연결하기 위한 임시 상태 저장과 탐지 결과 보관에 사용한다. 두 용도의 테이블 구성은 이후 설계에서 결정한다.

관제 적재 프로그램은 DynamoDB의 탐지 결과를 읽어 OpenSearch에 저장한다. 같은 결과가 반복 적재되지 않도록 고유한 `alert_id`를 사용한다. Lambda가 OpenSearch에 직접 접속하는 구성으로 가정하지 않는다.

## 개발·배포 순서

1. 민감정보를 제거한 샘플 CloudTrail JSON으로 탐지 로직을 로컬에서 검증한다.
2. OpenSearch와 Dashboards를 로컬 Docker Compose에서 개발한다.
3. 중간발표 전에 EC2에서 Docker 구성을 실행하고 실제 AWS 탐지 결과를 연결한다.
4. 발표 당일 이전에 행동 재현부터 관제 화면까지 전체 흐름을 검증한다.

| 담당 | 책임 |
| --- | --- |
| 1팀 | 실험용 IAM 환경 설정, 행동 재현, 실제 로그 확보, 정상 비교 사례, 실습 후 정리·복구 절차 |
| 2팀 | CloudTrail 수집 설정, EventBridge·Lambda 연결, 이벤트 분석, 상태 저장, 탐지 결과 JSON 생성 |

PL은 2팀 역할도 함께 맡는다.

## 저장소 구조

```text
infra/       공통 Terraform
scenarios/   행동 재현 코드와 정리·복구 절차
detection/   탐지 로직과 Lambda 코드
platform/    Docker 구성, 관제 적재 코드, 대시보드 설정
samples/     이벤트 및 탐지 결과 예시
```

빈 작업 폴더에는 Git이 폴더를 추적할 수 있도록 `.gitkeep`을 둔다. 실제 코드와 설정이 추가되면 해당 폴더의 `.gitkeep`은 제거할 수 있다.

`samples/`에는 [첫 시나리오 공통 JSON 초안](samples/README.md)과 EventBridge 입력 두 개, 탐지 결과 예시가 있다. 팀 검토용 문서이며 규격은 아직 확정하지 않았다.

## 중간발표 완료 기준

실제 AWS에서 첫 시나리오를 재현하면 탐지 결과가 생성되어야 한다. 관제 화면에서는 다음 정보를 확인할 수 있어야 한다.

- 대상 IAM 사용자
- 실제 이벤트 발생 시간
- 검토가 필요한 이유
- 두 근거 이벤트의 로그와 시간 흐름

## 작업 원칙

- 현재 저장소와 변경사항을 먼저 확인하고 기존 작업을 보존한다.
- 구현이나 AWS 리소스가 이미 존재한다고 가정하지 않는다.
- 코드와 설정의 의미를 초보 팀원도 이해할 수 있게 설명한다.
- 실제 AWS 자격 증명과 비밀번호를 코드나 샘플에 넣지 않는다.
- 샘플 로그는 민감정보를 제거한 예시로 준비한다.
- Python 가상환경, 비밀 설정, Terraform 상태·계획, 로컬 OpenSearch 데이터는 Git에서 제외한다.
- `.terraform.lock.hcl`과 비밀정보 없는 설정 예시는 Git에 포함한다. 예시 파일에도 실제 비밀정보를 넣지 않는다.

## 다음 작업: 공통 JSON 규격 확정

2팀의 탐지 결과를 3팀의 적재 프로그램과 관제 화면에서 일관되게 사용하려면 다음 사항을 함께 결정해야 한다.

| 결정 항목 | 합의할 내용 |
| --- | --- |
| 입력 이벤트 형태 | CloudTrail 원본과 EventBridge 감싸기 구조 중 샘플·탐지 입력 형태, 필수 필드, 누락 필드 처리 |
| 실행 주체와 대상 | 주체 유형·식별자, 대상 사용자의 계정·이름·ARN 등 식별 기준, 서로 다른 계정의 동명이인 구분 |
| 시간과 성공 판정 | UTC 시간 표현 및 정밀도, 10분 경계와 동시각 처리, 두 API의 성공·실패 판정 기준 |
| 중복과 순서 변경 | 이벤트 고유 식별자, 역순 도착 처리, 허용 지연과 상태 보관 기간, 여러 키 생성·정책 부착 시 연결 방식 |
| 탐지 결과 | 규격 버전, 시나리오 ID, 검토 필요 상태, 대상·주체·발생 시간·판단 이유·근거 이벤트 필드 |
| `alert_id` | 재처리해도 같은 결과에 같은 ID를 부여하는 생성 규칙과 탐지 결과의 단위 |
| 근거와 민감정보 | 근거 이벤트 원문 또는 필요한 필드의 보관 범위, 마스킹 기준, 샘플 익명화 규칙 |
| 적재 계약 | DynamoDB 탐지 결과 키·조회 방식, 재시도·진행 위치 관리, OpenSearch 문서 ID와 필드 자료형 |
