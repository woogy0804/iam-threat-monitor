# AWS IAM 행동 흐름 탐지 프로젝트

AWS에서 누가 누구에게 어떤 작업을 했는지 확인하고, 여러 이벤트를 연결해 검토가 필요한 흐름을 관제 화면에 보여주는 프로젝트입니다. 6명이 2명씩 3개 팀으로 진행하며, 중간발표는 **2026년 10월 8일**입니다.

## 첫 시나리오

테스트 IAM 사용자의 액세스 키가 생성된 뒤, 10분 이내에 같은 사용자에게 관리형 정책이 부착되면 두 이벤트를 연결합니다.

```text
CreateAccessKey 성공 → 같은 대상 사용자 → 10분 이내 AttachUserPolicy 성공
```

결과는 **검토 필요**로 표시합니다. 정상적인 계정 설정에서도 발생할 수 있으므로 공격이라고 확정하지 않습니다.

작업을 실행한 사람과 작업 대상 사용자는 다를 수 있습니다. 연결할 때는 대상 계정과 사용자 이름을 비교하며, 시간은 로그가 도착한 시각이 아닌 실제 이벤트 발생 시각을 사용합니다. 중복 전달과 순서가 바뀐 입력도 처리해야 합니다.

## 현재까지 준비한 내용

2026년 10월 3일 문서 정리 기준입니다.

| 항목 | 상태 |
| --- | --- |
| 저장소 기본 폴더와 Git 제외 설정 | 준비 완료 |
| EventBridge 입력 2개와 탐지 결과 JSON 예시 | 초안 작성 완료, 실제 로그와 비교 필요 |
| 작업용 IAM 로그인·MFA, AWS CLI·Terraform | PL 환경 설정 및 연결 확인 완료 |
| CloudTrail과 S3 로그 보관 구성 | Terraform 배포 완료, 10월 2일 AWS 조회에서 기록 시작 확인 |
| EventBridge·Lambda·DynamoDB | 아직 구현하지 않음 |
| OpenSearch·Dashboards·EC2 관제 환경 | 아직 구현하지 않음 |

현재 배포된 것은 로그 수집의 기반입니다. 첫 시나리오의 실제 로그 수신부터 관제 화면까지 연결한 상태는 아닙니다.

## 만들 흐름

```text
테스트 IAM 행동
  → CloudTrail: AWS 작업 기록
  → EventBridge: 필요한 이벤트 선택
  → Lambda: 두 이벤트 연결 및 탐지
  → DynamoDB: 연결 상태와 탐지 결과 보관
  → 관제 적재 프로그램: 결과를 읽어 OpenSearch에 저장
  → OpenSearch Dashboards: 목록과 근거 표시
```

S3에는 CloudTrail 원본 로그 파일을 보관합니다. DynamoDB는 탐지용 데이터 저장소입니다. Lambda와 OpenSearch 사이는 관제 적재 프로그램으로 연결하며, 같은 결과는 `alert_id`를 사용해 중복 적재를 막습니다.

| 담당 | 역할 | 작업 폴더 |
| --- | --- | --- |
| 1팀 | 첫 시나리오 연구, 테스트 환경·행동 재현, 로그 확보, 정상 비교와 복구 절차 | `scenarios/`, `samples/` |
| 2팀 | EventBridge·Lambda 연결, 실제 입력 확인, Python 탐지, DynamoDB 상태·결과 저장 | `detection/`, `samples/` |
| 3팀 | Docker, OpenSearch·Dashboards, 샘플 화면, 관제 적재 프로그램 | `platform/` |
| PL | 공통 Terraform, 계정·권한·예산, JSON 규격과 통합 조율 | `infra/` |

PL 신영욱은 1팀에도 참여합니다. AWS 공통 리소스의 배포는 PL과 조율하고, 각 팀은 필요한 설정과 기능 코드를 준비합니다.

## 발표에서 보여줄 것

실제 AWS에서 첫 시나리오를 실행하면 탐지 결과가 생성되고, 화면에서 **대상 사용자, 발생 시간, 판단 이유, 두 근거 이벤트의 시간 흐름**을 확인할 수 있어야 합니다.

탐지는 샘플 JSON으로, 관제는 로컬 Docker로 먼저 개발합니다. 이후 EC2에서 관제를 실행하고 실제 AWS 결과를 연결합니다. 추가 시나리오·Slack·GuardDuty·LLM 요약은 기본 흐름 완성 후 검토합니다.
